# Задание: Календарь звонков (Хекслет, проект 386)

Источник: Hexlet MCP `catalog_get_program_project` (slug `ai_assisted_development_calendar_slot_project_ru`), получено 2026-11-19. Шаги — со страниц проекта (H-AI/6 Проект Календарь звонков, пересобрано из HTML 2026-11-19).

## Общее описание

Проект учит вести разработку вместе с ИИ-агентом, пока сервис не заработает в сети. Вы соберёте сервис записи на звонок по мотивам Cal.com. Владелец публикует время для встреч, а гость выбирает свободный слот. Стек вы выбираете сами, приложение должно собираться в Docker-образ и запускаться в контейнере.

## Чему вы научитесь

Работать по циклу из разговора, спецификации, тикетов и реализации с набором скиллов в агенте. Вы будете описывать API в TypeSpec и получать из него OpenAPI и клиентский SDK, фиксировать решения в ADR и словаре проекта. Агент напишет код и тесты, вы проверите их сквозным сценарием в браузере, настроите CI с Conventional Commits и release-please, и выкатите сервис через MCP хостинга.

## Что получится в конце

Сервис работает по публичной ссылке. Владелец заводит типы встреч и видит все предстоящие записи. Гость выбирает тип встречи и свободное время в окне на 14 дней. Занятое время повторно не бронируется даже другим типом встречи. В репозитории лежат `Dockerfile`, `AGENTS.md`, TypeSpec-контракт, тесты, записанные решения и тикеты в GitHub Issues. Как это выглядит, показывают [скриншоты сервиса](https://files.hexlet.app/a/2ipc5m).

## Шаг 0. Описание проекта

### Чему учимся

В этом проекте мы проходим полный цикл разработки небольшого веб-приложения, где основным исполнителем выступает ИИ-агент. Сначала собираем каркас приложения и настраиваем агентную среду, затем проектируем функциональность через спецификацию, реализуем её по тикетам и публикуем сервис.

Работа идёт одним циклом: обсудили задачу, зафиксировали спецификацию, разложили её на тикеты, реализовали. Каждый шаг проекта называет, какой скилл вызвать и что должно остаться в репозитории после него.

Ключевой формат работы в этом проекте: всю разработку ведём с помощью ИИ-агентов. В идеале вы не пишете вручную ни одной строки кода: формулируете задачу агенту, проверяете результат и итеративно улучшаете решение.

Проект можно выполнить на любом стеке технологий. Ограничение задаёт итоговый результат: приложение должно собираться в Docker-образ и запускаться в контейнере. Такой формат позволяет сосредоточиться на процессе разработки и на устройстве приложения.

### Описание проекта

«Запись на звонок» это упрощённый сервис бронирования времени по мотивам *Cal.com*.

[изображение]

[Cal.com](https://cal.com/) это сервис, где пользователь публикует доступные интервалы, а другой человек выбирает свободное время и бронирует встречу. У нашего приложения тот же базовый сценарий: владелец публикует доступное время для встреч, а другой пользователь выбирает свободный слот и записывается на звонок.

В проекте нет авторизации, личных кабинетов и интеграций с внешними календарями. Функциональность намеренно ограничена, чтобы сосредоточиться на главном.

В результате должно получиться небольшое, но законченное приложение.

Владелец календаря в приложении один и задан заранее. Он заводит типы встреч, у каждого есть название, описание и длительность, и смотрит список предстоящих встреч всех типов. Гость заходит без регистрации, выбирает тип встречи, открывает календарь на ближайшие 14 дней и записывается на свободный слот. Слот длится столько, сколько выбранный тип встречи. Одно и то же время нельзя занять дважды, даже разными типами встреч.

Этого достаточно, чтобы пройти весь путь от проектирования до запуска сервиса в облаке.

Стек вы выбираете сами. Обязательная часть работы с API состоит из TypeSpec-контракта, сгенерированной OpenAPI-спецификации и клиентского SDK для фронтенда. До выбора инструментов проверьте, что для языка фронтенда есть генератор клиента из OpenAPI. Серверные типы и маршруты генерируются, если выбранный фреймворк это поддерживает. При отсутствии серверного генератора бекенд реализуется по контракту и проверяется тестами.

Окно записи занимает 14 календарных дней и сдвигается с течением времени. Начало с сегодняшнего или завтрашнего дня, часы работы владельца и часовой пояс вы выбираете и записываете в спецификации. Длительность слота совпадает с длительностью типа встречи, шаг доступных стартов тоже фиксируется в спецификации. Пересечение интервалов запрещено, включая частичное наложение разных типов. Следующая встреча может начинаться в момент окончания предыдущей. Правила действуют и для двух запросов, пришедших одновременно.

Данные можно хранить в памяти процесса. В этом случае перезапуск сбрасывает записи, и это ограничение нужно назвать в *README.md*. База с сохранением данных тоже допустима. Хранение после перезапуска отдельным условием приёмки не является.

## Шаг 1. Каркас приложения

На этом шаге мы собираем каркас: бекенд, фронтенд, программу запуска тестов, линтеры и прогон проверок в GitHub Actions. Функциональности здесь пока нет, появляется рабочая основа, на которую дальше кладутся фичи.

Главный ориентир шага это официальный getting started вашего фреймворка. Открывайте документацию и идите по ней, а команды может выполнять агент. Причина такая: модель помнит прошлые версии инструментов и уверенно предлагает устаревший способ создать проект, подключить сборку или программу запуска тестов. Документация фреймворка показывает актуальный способ, и каркас, собранный по ней, потом не приходится разбирать.

Стек вы выбираете сами. Рекомендуем TypeScript и Vite, для интерфейса shadcn/ui или Mantine: с ними агенты дают более точные подсказки, а типы упрощают правки по ходу проекта. Это рекомендация, вы можете взять свои инструменты.

До выбора стека проверьте цепочку TypeSpec, OpenAPI и генератор SDK для языка фронтенда. Клиентский SDK обязателен. Для бекенда генерация типов, схем проверки запросов и маршрутов зависит от фреймворка. Если подходящего серверного генератора нет, реализуйте сервер по контракту и проверьте совпадение тестами.

Тестов на функциональность здесь ещё нет, поэтому в CI достаточно одного дымового теста: приложение поднимается и отвечает. Задача шага в том, чтобы прогон тестов и линтера работал автоматически до появления первой фичи.

Программа запуска тестов находит тесты, выполняет их и сообщает результат. Для JavaScript и TypeScript это может быть Vitest, для Python pytest, для Java JUnit с задачей сборщика. GitHub Actions запускает выбранную вами команду на машине CI. В этом шаге достаточно одного дымового теста, который проверяет запуск приложения и успешный ответ на запрос. Проверки полного сценария бронирования появятся вместе с функциональностью.

Рекомендуем использовать mise для всего окружения разработки. В *mise.toml* фиксируются версии инструментов, переменные окружения, задачи установки, запуска, сборки и проверок. Хуки mise позволяют запускать задачи при установке инструментов или входе в проект. Git-хуки рекомендуем настроить через hk, установленный с помощью mise, и вызывать из них те же проверки. Фоновые серверы и сервисы разработки описываются через daemons mise, чтобы агент мог запускать, останавливать их и смотреть состояние. Для daemons включите `experimental = true` в разделе `[settings]` и зафиксируйте версию pitchfork, который управляет процессами.

Соберите проверки в одну задачу, например `mise run check`. Сейчас она запускает линтер, проверку типов, если она есть в стеке, и дымовой тест. GitHub Actions вызывает эту же команду. По мере разработки в неё добавляются остальные тесты. Выбор другого инструмента допустим, команды и версии должны быть воспроизводимыми.

При выборе инструментов используйте [dev-guardrails](https://github.com/mokevnin/dev-guardrails). В подборке для каждой задачи названы рекомендуемый инструмент, причины выбора и ограничения. Начните с инструментов для своего стека, Git-хуков и CI. Подключайте их к общей команде проверок.

Сразу договоритесь о формате Conventional Commits (`feat:`, `fix:` и так далее) и запишите правило в *AGENTS.md*. Автоматические релизы через release-please подключим на шаге реализации после первой функции. На этапе каркаса их настраивать не нужно.

В конце шага запустите в агенте команду инициализации (`/init` в OpenCode и Claude Code). Агент изучит собранный каркас и предложит *AGENTS.md*: файл с рабочими правилами проекта, который попадает в контекст в начале каждой сессии. Порядок именно такой: на пустом репозитории инициализации нечего изучать, а после каркаса в проекте уже есть команды запуска, тестов и линтера, и они попадают в файл.

Полученный *AGENTS.md* стоит сократить. Агент почти всегда пишет туда лишнее, а рабочий файл короткий: команды, устройство проекта и правила, которые из кода не читаются. Если команды уже описаны в другом документе проекта, например в *CONTRIBUTING.md*, *AGENTS.md* может ссылаться на него. Тогда команды хранятся в одном месте и не расходятся между файлами.

#### Требования

- Бекенд и фронтенд запускаются локально.

- В проекте есть команды запуска тестов и линтера.

- Одна команда запускает все текущие проверки локально и в GitHub Actions на каждый push, прогон зелёный. Версии инструментов зафиксированы в проекте.

- Коммиты идут по Conventional Commits.

- В корне репозитория есть *AGENTS.md*. Из него агент находит команды запуска, тестов и линтера и правило про формат коммитов: они записаны в самом файле или в документе, на который файл ссылается.

- *AGENTS.md* короткий и без противоречивых правил. В нём только команды, устройство проекта и правила, которые из кода не читаются.

## Шаг 2. Скиллы и агентная среда

Дальше проект идёт по одному циклу: обсудили задачу, зафиксировали спецификацию, разложили её на тикеты, реализовали. Этот цикл собран в набор скиллов, и на этом шаге мы подключаем его к репозиторию.

Скилл это переиспользуемый сценарий работы: директория с файлом `SKILL.md`, где записано, что делать, в каком порядке и какие проверки выполнить. Агент подгружает скилл, когда задача подходит по описанию, либо когда вы вызываете его явно командой со слэшем. Мы берём набор инженерных скиллов Мэтта Покока: он ставится одной командой и работает в любом совместимом агенте.

Дальше шаги называют скиллы через слэш, например `/wayfinder`. В Claude Code это готовая команда. В OpenCode скиллы набора командами через слэш не появляются, поэтому скилл вызывается просьбой к агенту по имени («Запусти скилл wayfinder») или ссылкой на его файл: `@.agents/skills/wayfinder/SKILL.md`.

Скилл ведёт диалог по своей инструкции. Проверьте, что вызван именно нужный скилл, и читайте его результат перед переходом к следующему действию. Шаги проекта называют, какой скилл вызвать и что должно получиться на выходе, а дальше скилл ведёт вас вопросами.

После установки набор нужно настроить под репозиторий. Скиллы заводят задачи, публикуют спецификации и размечают тикеты, поэтому им нужно знать, где у проекта трекер. Настройку делает отдельный скилл `setup-matt-pocock-skills`: он изучает репозиторий, задаёт несколько вопросов и записывает ответы в *docs/agents/*.

На вопрос про трекер задач выберите GitHub Issues в репозитории проекта. Если скилл спросит про метки для разбора задач, оставьте значения по умолчанию. Проверьте в настройках пути документов предметной области. Словарь сохраняется в *GLOSSARY.md*, решения в *docs/adr/*.

Трекер здесь именно GitHub Issues, потому что дальше в нём живут карта решений, спецификация и тикеты. Всё это остаётся в репозитории проекта и открывается глазами, поэтому по нему видно, как шла работа.

В новой сессии передавайте агенту ссылку на задачу и просите прочитать *AGENTS.md* и записанные решения. Например, перед реализацией бронирования можно попросить «Запусти скилл implement-spec для спецификации #12 из этого репозитория. Сначала прочитай AGENTS.md, спецификацию, связанные тикеты и их зависимости». Ожидаемый результат вызова назван в каждом следующем шаге.

#### Требования

- Набор скиллов установлен и доступен в агенте.

- В репозитории есть *docs/agents/* с записанной конфигурацией трекера, меток и документов предметной области.

- В *AGENTS.md* появился раздел про скиллы.

#### Ссылки

- [Skills](https://skills.sh/): каталог скиллов и CLI для установки.

- [mattpocock/skills](https://github.com/mattpocock/skills): набор инженерных скиллов, который мы используем в проекте.

- [Работа с OpenCode](https://help.hexlet.io/ai/opencode): установка, вход и выбор модели, справка Хекслета.

#### Задачи

1. Установите набор скиллов: `npx skills@latest add mattpocock/skills`. Установщик спросит, для какого агента ставить и какие скиллы брать. Выберите своего агента и не снимайте отметку со скилла `setup-matt-pocock-skills`.

2. Проверьте, что агент видит скиллы, включая `implement-spec`: они должны появиться в списке доступных.

3. Запустите скилл `setup-matt-pocock-skills` и ответьте на его вопросы, как описано выше.

4. Посмотрите, что скилл записал в *docs/agents/* и в *AGENTS.md*. Проверьте адрес трекера, пути словаря и решений.

5. Начните новую сессию и попросите агента назвать трекер и рабочую команду проверок по файлам проекта. Исправьте настройки, если ответ не совпал с вашей конфигурацией.

#### Результат шага

Набор скиллов установлен и настроен под репозиторий: трекер, метки и документы предметной области зафиксированы в *docs/agents/*.

## Шаг 3. Первая фича: главная страница

Первую фичу берём небольшую: главную страницу приложения, которая рассказывает про сервис и ведёт на страницу записи. Смысл шага в том, чтобы пройти весь цикл работы целиком на задаче, где решений мало, и дальше применить его к бронированию.

Цикл начинается с разговора. Вызовите `/grill-with-docs`: агент проведёт интервью по задаче, будет задавать вопросы и спорить с ответами, а по ходу разговора начнёт складывать документы предметной области. На выходе появляются две вещи: словарь проекта в *GLOSSARY.md* и принятые решения в *docs/adr/*.

Передайте агенту сценарий и ограничения из введения. Интервью касается главной страницы. Решения по остальным функциям можно записывать вопросами для карты следующего шага, их не нужно принимать заранее.

Интервью здесь несёт основную работу шага. Агент про ваш проект не знает ничего: ни как выглядит главная страница, ни что на ней должно быть, ни какие решения вы уже приняли. Разговор это способ передать ему это знание один раз и оставить его в репозитории, чтобы не пересказывать в каждой новой сессии.

Словарь дальше держит единый язык. Если страницу выбора вы называете каталогом типов встреч, так она называется и в тикетах, и в коде, и в тестах. Расхождение в словах стоит дорого: агент начинает заводить вторую сущность там, где имелась в виду прежняя.

Дальше реализация. Вызовите `/implement`: скилл берёт результат разговора, пишет код вместе с тестами, проходит ревью и коммитит результат. Отдельного шага под тесты в проекте нет, они появляются вместе с кодом.

#### Требования

- Главная страница открывается и ведёт на страницу записи. До реализации бронирования на следующем этапе допустима заглушка этой страницы.

- Есть тесты на главную страницу, прогон в GitHub Actions зелёный.

- В репозитории есть *GLOSSARY.md* со словарём проекта.

- Принятые решения записаны в *docs/adr/*.

#### Ссылки

- [Architecture Decision Records](https://adr.github.io/): формат записи принятых решений.

#### Задачи

1. Передайте агенту сценарий и ограничения из введения, вызовите `/grill-with-docs` и пройдите интервью по главной странице.

2. Проверьте, что в *GLOSSARY.md* появился словарь проекта, а в *docs/adr/* принятые решения.

3. Вызовите `/implement` и реализуйте страницу вместе с тестами.

4. Убедитесь, что прогон в GitHub Actions зелёный.

#### Результат шага

Главная страница работает и покрыта тестами, в репозитории появились словарь проекта и записанные решения.

## Шаг 4. Проектирование бронирования

Основная функциональность проекта это запись на звонок: типы встреч, календарь свободных слотов, бронирование и список встреч владельца. Работы здесь на несколько сессий, и большинство решений ещё не принято, поэтому проектируем её картой решений.

Начните с `/wayfinder`. Скилл заводит в трекере карту: одну задачу, к которой прицеплены дочерние задачи. Каждая такая задача это вопрос, ответ на который надо принять до реализации: какие сущности есть в контракте, как устроена модель слотов, что происходит при конфликте между разными типами встреч, на каких границах проверять приложение тестами. Карта разбирается по одной задаче за сессию, и несколько заходов это нормальный ход работы.

Пункт назначения карты должен вести к согласованной спецификации приложения, по которой можно создавать тикеты. Своими словами назовите этот результат. Буквальное совпадение с примером не требуется, важно сохранить границы задачи.

#### Design First и контракт

Этот раздел объясняет, зачем приложению контракт и как из него получается код. На этом шаге вы готовите спецификацию и тикеты. Генерацию контракта и SDK вы настроите в первом тикете следующего шага «Реализация».

Приложение делается в подходе Design First: сначала фиксируем поведение системы и API-контракт, потом реализуем фронтенд и бекенд по нему раздельно. Контракт задаёт границу между частями приложения и остаётся единым источником правды.

Для агентов это даёт конкретный выигрыш: имея явную спецификацию, они не разбирают внутреннюю реализацию соседней части приложения, и расход токенов падает. При изменениях достаточно обновить контракт и синхронно внести правки в обе части.

Контракт описываем в TypeSpec, а OpenAPI-спецификацию из него генерируем. TypeSpec это компактный язык описания API: сущности и эндпоинты записываются коротко и разворачиваются в полноценную OpenAPI. Писать и поддерживать большой OpenAPI руками громоздко, в нём легко ошибиться и разойтись с реальностью.

Посмотрим на простом примере. Опишем тип события и эндпоинт для получения их списка:

```
import "@typespec/http";

using TypeSpec.Http;

model EventType {
  id: string;
  title: string;
  durationMinutes: int32;
}

@route("/event-types")
interface EventTypes {
  @get list(): EventType[];
}
```

После генерации в OpenAPI-спецификации появляется описание маршрута и модели. Ниже показан фрагмент с этими частями.

```
paths:
  /event-types:
    get:
      operationId: EventTypes_list
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/EventType'
components:
  schemas:
    EventType:
      type: object
      required: [id, title, durationMinutes]
      properties:
        id: {type: string}
        title: {type: string}
        durationMinutes: {type: integer, format: int32}
```

Несколько строк описания разворачиваются в подробный контракт. Именно по нему фронтенд и бекенд реализуются независимо друг от друга.

Спецификация это не конечная точка цепочки. Из неё генерируется клиентский SDK для фронтенда: типы запросов и ответов вместе с функциями вызова эндпоинтов. Фронтенд тогда обращается к API через сгенерированный клиент, и часть расхождений обнаруживается при проверке типов ещё до запуска. На бекенде из той же спецификации генерируются свои артефакты (типы, схемы проверки запросов и заготовки маршрутов), если для фреймворка есть генератор. Состав зависит от фреймворка. Если генератора нет, серверную часть пишут по контракту, а совпадение с ним проверяют тесты.

```
TypeSpec ──> OpenAPI ──┬──> клиентский SDK (фронтенд)
                       └──> серверные артефакты (если есть генератор)
```

Генерация обновляет артефакты по контракту. Она не доказывает, что фронтенд использует клиент и что сервер возвращает описанные ответы. Эти свойства проверяются отдельно на следующем шаге. Инструменты генерации выбирайте под свой стек. Команды хранятся в *Makefile* или в скриптах пакета, чтобы цепочка повторялась одним вызовом.

#### Что должно уметь приложение

В проекте есть две условные роли: владелец календаря и гости. Регистрации и авторизации нет. Владелец календаря это один заранее заданный профиль, который по умолчанию используется в админской части. Гость бронирует слоты без создания аккаунта и без входа в систему.

Владелец календаря может:

- Создавать типы событий. Для каждого типа события задаёт id, название, описание и длительность в минутах.

- Просматривать страницу предстоящих встреч, где в одном списке показаны бронирования всех типов событий.

Гость:

- Может посмотреть страницу с видами брони, где доступно название, описание и длительность.

- Выбирает тип события, открывает календарь и выбирает свободный слот в ближайшие 14 дней.

- Создаёт бронирование на выбранный слот.

Правило занятости:

- Интервалы двух записей не пересекаются, даже для разных типов событий и одновременных запросов. Например, после брони с 10:00 до 11:00 запись с 10:30 до 11:00 отклоняется. Запись с 11:00 допустима.

- Если гость пытается занять уже занятое время, он видит понятное сообщение о конфликте.

Окно записи по умолчанию:

- Окно записи сдвигается с текущей датой и занимает 14 календарных дней. С какого дня оно начинается, с сегодняшнего или с завтрашнего, решите сами и запишите в спецификацию.

- Слоты формируются в рабочие часы владельца, например с 09:00 до 18:00. Часы работы и часовой пояс, в котором они заданы, тоже записываются в спецификацию.

- Слот длится столько, сколько выбранный тип события. Шаг доступных стартов запишите в спецификации. Он может совпадать с длительностью типа или быть общим для всех типов.

- Гость может записаться только на свободный слот из этого окна.

Внутреннюю реализацию, стек и структуру проекта вы выбираете сами. Здесь мы договариваемся о внешнем поведении системы: какие сценарии поддерживаются, какие данные передаются и какие ограничения действуют при бронировании.

#### Спецификация и тикеты

Когда решения по карте приняты, соберите их в спецификацию: вызовите `/to-spec`. Этот скилл интервью не проводит, он синтезирует спецификацию из того, что уже обсуждено, поэтому запускать его надо в сессии, где карта и ответы по её задачам загружены в контекст. Спецификация публикуется в трекер и содержит пользовательские истории, принятые решения по реализации и решения по тестированию: на каких границах приложение проверяется.

Дальше разложите спецификацию на тикеты: `/to-tickets`. Тикеты получаются вертикальными: каждый проходит через все слои приложения (контракт, сервер, интерфейс, тесты) и проверяется по отдельности. Каждый тикет объявляет, какие тикеты его блокируют, поэтому всегда видно, что можно брать в работу.

Первый тикет реализации должен проверить всю контрактную цепочку на небольшой функции. Например, получение списка типов встреч проходит через TypeSpec, OpenAPI, сгенерированный SDK, сервер и отображение результата на странице. В тикете запишите команды генерации и проверку ответа API. На этом шаге вы готовите постановку и план, код цепочки появится на следующем.

Тикеты, использующие контрактную цепочку, должны зависеть от её настройки. В спецификацию и тикеты включите общую команду проверок, API-тесты, браузерный сценарий, проверку одного теста с временно нарушенным правилом бронирования и настройку release-please после первой функции. На следующем шаге весь граф выполняет `/implement-spec`.

#### Требования

- В трекере есть карта решений, её вопросы закрыты с записанными ответами.

- В спецификации описаны роли владельца и гостя, типы встреч, окно 14 дней, рабочие часы, часовой пояс, длительности, шаг стартов, примыкание и конфликты интервалов.

- Спецификация задаёт API и ожидаемые ответы, включая создание бронирования, ошибки данных и конфликт занятого времени. Пути, методы и поля вы выбираете сами.

- Названы границы тестирования, включая прямые запросы к API и браузерный сценарий с настоящим сервером.

- В трекере есть тикеты с зависимостями и ссылками на спецификацию. Первый тикет проводит одну небольшую функцию через контракт, генерацию, сервер, интерфейс и тесты.

#### Ссылки

- [TypeSpec](https://typespec.io/): язык описания API, из которого генерируется OpenAPI-спецификация.

- [openapi-ts](https://heyapi.dev/): генерация типизированного клиентского SDK из OpenAPI-спецификации.

- [OpenAPI Generator](https://openapi-generator.tech/): генераторы клиента и серверных заготовок под разные языки и фреймворки.

#### Задачи

1. Вызовите `/wayfinder` и заведите карту решений для согласованной спецификации приложения.

2. Разбирайте вопросы карты по одному. Записывайте ответы в трекер, учитывая ограничения первого шага. Рассчитывайте на несколько сессий.

3. Вызовите `/to-spec` в сессии, где загружены карта и ответы. Прочитайте полученную спецификацию, проверьте роли, правила времени, API и решения по тестированию.

4. Вызовите `/to-tickets` и проверьте зависимости. У первого тикета должен быть небольшой работающий результат через всю контрактную цепочку. Убедитесь, что граф включает проверки и настройку release-please, затем передайте спецификацию с тикетами в `/implement-spec` на следующем шаге.

#### Результат шага

В трекере есть карта с решениями, согласованная спецификация приложения и проверяемые тикеты с зависимостями. Можно начинать реализацию без новых функциональных ограничений.

## Шаг 5. Реализация

Спецификация и тикеты готовы. Вызовите `/implement-spec` и передайте ссылку на спецификацию в GitHub Issues. Попросите прочитать *AGENTS.md*, связанные тикеты и их зависимости. Скилл берёт в работу всю спецификацию и собирает реализацию в одной общей ветке.

Тикеты образуют граф зависимостей. Скилл сам выбирает готовые к работе тикеты, запускает исполнителей в отдельных рабочих копиях и объединяет результаты в общей ветке. Независимые задачи могут выполняться параллельно. Настройка контрактной цепочки предшествует задачам, которые её используют.

Исполнители пишут код через цикл TDD и проверяют границы, заданные спецификацией. После выполнения тикетов `/implement-spec` запускает общее ревью ветки и исправляет его замечания. Если работа сдаётся через pull request, скилл готовит его к ревью. От вас нужно следить за ходом работы, отвечать на вопросы агента и проверить итоговый результат.

Основной сценарий бронирования проверяется в браузере: гость выбирает тип встречи, открывает календарь, занимает свободный слот и видит подтверждение, а владелец видит эту встречу в своём списке. Этот сценарий закрепляется браузерным тестом в репозитории, рекомендуем Playwright. Ручную проверку после следующей правки никто не повторит, а тест запускается одной командой и показывает, что сценарий по-прежнему проходит.

Правила бронирования должны выполняться на сервере. Проверка занятости только в интерфейсе обходится любым другим клиентом: прямой запрос в API создаст вторую запись на то же время.

Обращения к API идут через сгенерированный клиентский SDK. Руками написанный вызов `fetch` рядом с готовым клиентом уводит фронтенд от контракта, и расхождение всплывает уже на живом приложении. Если контракт по ходу работы меняется, порядок такой: правка TypeSpec, генерация, затем код обеих сторон.

Коммит реализации ссылается на тикет, который он закрывает, например `feat: запись на свободный слот (#12)`. GitHub превращает номер в ссылку, и по истории видно, какой коммит какую задачу делал. До вызова `/implement-spec` запишите это правило в *AGENTS.md* рядом с правилом про формат коммитов.

#### Контрактная цепочка и проверки

Проверьте результат первого тикета. Нужная операция описана в TypeSpec, OpenAPI и клиентский SDK сгенерированы, страница обращается к серверу через клиент. Если фреймворк поддерживает серверный генератор, добавлены его артефакты. Сервер без такого генератора реализован по контракту. Команды всей генерации объединены в один вызов.

В *AGENTS.md* должны быть названы генерируемые пути и записан запрет править их руками. Если артефакты коммитятся, CI повторяет генерацию и проверяет изменения, включая новые файлы. Если они не коммитятся, CI генерирует их из чистого состояния перед сборкой и тестами. Отдельно проверьте, что обращения фронтенда к контрактному API идут через SDK, а коды и тела ответов настоящего сервера совпадают с контрактом.

Общая команда проверок теперь запускает линтер, проверку типов, API-тесты и браузерный тест. Браузерный тест работает с запущенным приложением, без подмены ответов API бронирования. Один зелёный тест главной страницы из каркаса всего этого не подтверждает.

#### Проверка теста

В одном из тикетов агент проверяет чувствительность теста к ошибке. Например, в отдельной рабочей копии временно нарушает запрет частичного пересечения разных типов встреч и запускает защищающий тест. Тест должен упасть на проверке соответствующего поведения. Если он остаётся зелёным, агент дополняет тест, затем восстанавливает правильную реализацию и получает зелёный результат. Сломанная версия сервиса не публикуется.

Проверьте, что в тикете сохранены название правила, команда, результаты красного и зелёного запусков и короткое объяснение причины падения.

Настройка release-please тоже входит в граф тикетов и выполняется после первой функции. Агент подключает отдельный workflow, который использует Conventional Commits для подготовки release-PR. Проверьте, что после изменения основной ветки workflow создаёт release-PR.

#### Требования

- Сквозной сценарий гостя проходится целиком: выбор типа встречи, календарь, запись на свободный слот, подтверждение.

- Одна команда из *AGENTS.md* запускает все проверки локально и в CI, включая браузерный сценарий с настоящим сервером без подмены ответов API бронирования.

- Занятый слот не предлагается как свободный, повторная запись на это время не проходит, в том числе для другого типа встречи.

- При конфликте слота гость видит понятное сообщение.

- Правила бронирования выполняются на сервере.

- Есть страница владельца со списком предстоящих встреч всех типов.

- В репозитории есть TypeSpec-контракт, OpenAPI и клиентский SDK генерируются одной командой. Серверные артефакты генерируются, если для фреймворка есть подходящий генератор.

- Реализация совпадает с контрактом по путям, методам, полям, успешным ответам и ошибкам данных и конфликта. API-тесты проверяют эти ответы.

- Генерация повторяется в CI. Генерируемые пути и запрет ручных изменений записаны в *AGENTS.md*.

- Фронтенд обращается к API через сгенерированный клиентский SDK.

- Тесты покрывают основной сценарий бронирования и конфликт слотов, прогон в GitHub Actions зелёный.

- Тест на конфликт проверяет и частичное наложение встреч разной длительности, например встречу на 60 минут в 10:00 и встречу на 30 минут в 10:30.

- Коммиты реализации ссылаются на тикеты, правило записано в *AGENTS.md*.

- Тикеты спецификации выполнены через `/implement-spec`, результаты собраны в одной ветке и прошли общее ревью.

- В тикете есть результат проверки одного теста с временно нарушенным правилом и после восстановления.

- release-please подключён и создаёт release-PR.

#### Ссылки

- [release-please](https://github.com/googleapis/release-please) подготавливает релизы по Conventional Commits.

- [release-please-action](https://github.com/googleapis/release-please-action) запускает release-please в GitHub Actions.

- [Playwright MCP](https://github.com/microsoft/playwright-mcp): запуск браузерных сценариев и автоматизация пользовательских действий через агента.

- [Chrome Devtools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp): диагностика проблем в браузере, включая сеть, консоль и состояние страницы.

#### Задачи

1. Допишите в *AGENTS.md* правило, что коммит ссылается на тикет.

2. Вызовите `/implement-spec` со ссылкой на спецификацию и связанные тикеты. Следите за ходом реализации и отвечайте на вопросы агента.

3. Проверьте итоговую ветку или pull request, включая контрактную цепочку, общий прогон проверок, браузерный сценарий и результаты эксперимента с тестом.

4. Передайте замечания агенту, получите исправления и убедитесь, что GitHub Actions зелёный. После ревью внесите результат общей ветки в основную и проверьте появление release-PR.

## Шаг 6. Docker и деплой

На этом шаге мы готовим приложение к запуску в продакшене. Сделаем это с помощью Docker. Он позволяет упаковать приложение и его окружение в один образ, который одинаково запускается локально, в CI и в облаке: различий между средами меньше, и запуск проще повторить на любой платформе.

Деплой тоже отдаём агенту. Для деплоя подойдёт Render. Его бесплатный тариф запускает веб-сервис из Docker-образа и выдаёт ему публичную ссылку, а через MCP-сервер Render агент сам создаёт сервис, выкатывает образ и проверяет, что приложение отвечает. Подключите MCP-сервер Render и попросите агента провести выкат.

Бесплатный сервис засыпает после 15 минут без запросов, поэтому первый запрос после паузы отвечает дольше обычного. Для сдачи проекта этого достаточно.

Конфигурация MCP хранится в проектном файле вашего агента или в безопасном шаблоне с инструкцией подключения. Имя зависит от агента, например OpenCode использует *opencode.json*, Codex использует *.codex/config.toml*. При входе по OAuth опишите процедуру, данные сессии в Git не добавляются. API-ключ можно получать из переменной окружения. Файлы с реальными ключами исключите из Git, а шаблон оставьте в репозитории.

По итогам шага должен получиться Docker-образ, при запуске которого приложение автоматически стартует внутри контейнера, и публичная ссылка на работающий сервис.

#### Требования

- В корне репозитория должен лежать файл *Dockerfile*. По нему в проверке собирается образ и запускается приложение.

- При запуске контейнера из собранного образа приложение должно стартовать автоматически.

- Приложение должно запускаться в контейнере по порту из переменной окружения `PORT`. Эта переменная используется и при деплое, и в автоматической проверке проекта.

- После деплоя у приложения должна быть публичная ссылка, и она добавлена в репозиторий.

- В репозитории есть проектная конфигурация MCP выбранного агента или безопасный шаблон с инструкцией. Вход через OAuth и переменные окружения допустимы.

- По публичной ссылке проходит сценарий гостя и владельца, включая отказ повторного бронирования. В *README.md* описано, сбрасываются ли данные после перезапуска.

- В истории репозитория нет ключей, токенов и других секретов.

#### Ссылки

- [Render MCP](https://render.com/docs/mcp-server): MCP-сервер, через который агент автоматизирует деплой и проверку сервиса в Render.

- [Гайд Как деплоить приложение на Render](https://ru.hexlet.io/blog/posts/kak-deploit-prilozhenie-na-render-gayd-dlya-frontenderov-i-bekenderov)

- [Railway MCP](https://docs.railway.com/ai/mcp-server): запасной вариант, если Render недоступен. Позволяет агенту так же автоматизировать деплой и проверку сервиса, но уже в Railway.

#### Задачи

1. Соберите Docker-образ приложения.

2. Подключите MCP-сервер хостинга в конфигурации проекта и настройте деплой с запуском приложения по `PORT`. Проверьте работу приложения. Если Render недоступен, задеплойте на Railway: тот же Docker-образ, запуск по `PORT` и публичная ссылка. Для проверки платформа не важна, важно, чтобы приложение было опубликовано и работало по `PORT`.

3. По публичной ссылке создайте запись, проверьте её в списке владельца и убедитесь, что пересекающаяся запись отклоняется.

4. Добавьте в *README.md* ссылку, порядок подключения MCP без секретов и ограничение хранения данных.

#### После приёмки

Перед началом продолжения проекта перенесите принятые исправления в исходную версию второго проекта. Не заменяйте его файлы целиком, если там уже есть новые изменения. В *README.md* продолжения укажите, от какой версии первого проекта начали работу. Начинать второй проект ради сдачи первого не требуется.

#### Результат шага

Есть *Dockerfile* для сборки образа, приложение запускается в контейнере по `PORT` и доступно по публичной ссылке.
